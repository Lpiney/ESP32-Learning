# 03 · 摇杆双电机遥控器（Joystick Dual-Motor Controller）

一块 ESP32-S3 独立完成：**读摇杆 → 算差速 → 直接驱动两个电调 → 同时画到 OLED**。
不依赖电脑、不依赖别的板子。

```
   PS2 摇杆 ──> 算左右脉宽 ──> 两路 50Hz PWM ──> 电调 ×2
                  │
                  └──> 同一帧画到 OLED（屏幕上的数 = 电机收到的数）

   串口只是旁路：把同一份数据打出来，给电脑上的 Motor-Sim 看平面仿真
```

```
┌──────────────────────────────────────────────────────────┐
│ READY DEAD              L=1500                           │ ← 预热状态 + 死区状态
│                         R=1500                           │   左右实际输出脉宽(us)
│            · · · · · · · ·                               │
│          ·        ●        ·        X +0.42              │ ← 外圈虚线 = 行程边界 ±1.0
│         ·     · · · ·       ·       Y -0.17              │   内圈点线 = 死区 ±0.15
│        ·     ·   ✛   ·       ·                           │   实心点 = 当前摇杆位置
│         ·     · · · ·       ·                            │
│          ·                 ·                             │
│            · · · · · · · ·                               │
│  X ────────────────┄┄┄───────●────                       │ ← 一维展开，缺口 = 中点
│  Y ────────────────┄┄┄─────●──────                       │
└──────────────────────────────────────────────────────────┘
```

## 硬件

- ESP32-S3（本课按 **N16R8** 配置：16MB Flash）
- 0.96" OLED，**4 脚 I2C 版**（SSD1306，丝印 `GND VCC SCL SDA`）
- PS2 双轴摇杆模块（丝印 `GND +5V URX URY SW`，34×26mm）
- **两个电调（ESC）+ 两个电机**，各带动力电池
- 面包板 + 杜邦线

> ⚠️ 如果拿的是 8MB Flash 的板子（`default_8MB.csv` 那块），要改
> `platformio.ini` 里的 `board_build.partitions`、`board_upload.flash_size`、
> `board_upload.maximum_size` 三项再烧，否则提示分区超出。

## 接线

### OLED（4 脚 I2C）

| OLED 丝印 | 接到 ESP32-S3 |
|---|---|
| GND | GND |
| VCC | **3.3V** |
| SCL | GPIO9 |
| SDA | GPIO8 |

### 摇杆

| 摇杆丝印 | 接到 ESP32-S3 |
|---|---|
| GND | GND |
| +5V | **3.3V**（见下方说明） |
| URX | GPIO1 |
| URY | GPIO2 |
| SW | GPIO3 |

### 两个电调

| 电调细线 | 接到 ESP32-S3 |
|---|---|
| 信号（白/橙） | 左：**GPIO4**，右：**GPIO5** |
| 地（黑/棕） | GND（**必须和 ESP32 共地**） |
| 电源（红，BEC 5V） | **留空不接**（电调从动力电自己取电） |

另外电调还有两根粗线接动力电池（XT60），三根粗线接电机。

**电调的中立位必须先确认**（`src/main.cpp` 的 `PULSE_NEUTRAL`）：

| 电调类型 | 中立位 |
|---|---|
| 双向（能倒车，ROV 一般用这种） | `1500` ← 默认 |
| 单向（只能正转） | `1000` |

猜错的后果：**上电瞬间螺旋桨直接全速转**。所以第一次通电一定要先脱桨。

### 三个容易踩的坑

**1. 摇杆的 `+5V` 要接 3.3V，不要接 5V。**
模块印 `+5V` 是因为它原本配 5V 的 Arduino，但里面只有两个电位器，接 3.3V
完全正常。必须接 3.3V：摇杆输出是 `0~VCC`，供电 5V 就会超过 ESP32 的 ADC
量程（约 3.1V）甚至超过引脚耐压。

**2. URX/URY 必须是 ADC1 的通道（GPIO1~GPIO10）。**
ESP32-S3 有两组 ADC：ADC1（GPIO1~10）和 ADC2（GPIO11~20）。Arduino 的
`analogRead()` 只能可靠地用 ADC1；ADC2 被 WiFi 占用。所以选 GPIO1/GPIO2。

**3. ESP32 和两个电调必须共地。**
信号是相对 GND 的电压，不共地电调收到的是乱七八糟的电平。

### 引脚分配与避让

本课用：1、2、3（摇杆）+ 4、5（电调）+ 8、9（屏）。

| 要避开的引脚 | 原因 |
|---|---|
| GPIO33 ~ GPIO37 | **N16R8 的 8MB PSRAM 走 Octal 模式占用了**，接了必崩 |
| GPIO0 / GPIO45 / GPIO46 | 启动模式 strapping 脚 |
| GPIO19 / GPIO20 | 原生 USB D-/D+ |
| GPIO26 ~ GPIO32 | 板载 SPI Flash |
| GPIO43 / GPIO44 | UART0，留着看串口 |

GPIO3 也是 strapping 脚，但它上电要求高电平、内部上拉正好满足，当输入用没问题。

## 安全机制（重要）

**摇杆不需要按任何键，上电预热完就一直有效。** 只有两道闸：

1. **开机预热窗口 `BOOT_IGNORE_MS = 3000`**：上电后头 3 秒把摇杆当没动，
   输出固定中立。等电调自检响完、你手也放好了才开始响应。这期间屏幕左上角
   显示 `WAIT`，之后变 `READY`。
2. **油门限速 `SLEW_US_PER_MS = 2.0`**：脉宽每毫秒最多变 2µs，从 1500 到
   2000 要约 250ms，不会"啪"一下满油门。

> ⚠️ **代价要说清楚**：没有上锁开关之后，板子通电就随时可能转。
> 所以**测试时一定脱桨，手边留着电源开关**。
> 想恢复"必须手动解锁"就把预热窗口改成"等按键"，或者直接给电调动力电加个开关。

> **台面测试流程**：脱桨 → 只给 ESP32 上 USB 电、电调动力电先断开 →
> 确认屏幕亮、串口在刷 `JOY` → 接动力电 → 等左上角变成 `READY` →
> 轻推摇杆，确认两个电机转向正确。
> 转向对不对、要不要改代码，跑 `python3 tools/joy_check.py`，它会问你看
> 到的现象然后直接告诉你改哪一行。想量电调的实际行程（改 `PULSE_MIN` /
> `PULSE_MAX` 之前该做的），就只接一路电调、让固件输出固定脉宽，从 1000
> 开始每 10µs 往上加，记下"刚开始转"和"到顶"两个值。

## 摇杆 → 双电机映射

```
fwd = y（前后）,  turn = x（左右）
左 = fwd + turn        右 = fwd - turn        线性映射到 1000~2000µs，中立 1500
                              ↑ 后退（y<0）时 turn 取反，见下
```

先按死区 **线性重标定**（不是硬截断），所以刚离开死区时输出从 0 连续起步，
不会"一顿"。

| 摇杆 | 左 | 右 | 效果 |
|---|---|---|---|
| 居中（死区内） | 1500 | 1500 | 停 |
| Y=+100 | 2000 | 2000 | 两路同速（前提：两路电调都把 2000 当"前进"） |
| Y=-100 | 1000 | 1000 | 两路同速后退 |
| **X=+100（原地推右）** | 2000 | 1000 | 左路出力多 → 车头右转 |
| **X=-100（原地推左）** | 1000 | 2000 | 右路出力多 → 车头左转 |
| X=+100 且 Y=+100 | 2000 | 1500 | 前进中推右 → 车头往右偏 |
| **X=+100 且 Y=-100** | 1000 | 1500 | 后退中推右 → **车尾往右走** |

### 后退时转向为什么要取反

推右时，**前进车身漂向右、后退也漂向右** —— 这才是"手往哪推，车往哪走"的感觉。
为了做到这一点，后退时必须把左右取反：

| 摇杆 | 车身往哪边偏 | 车头朝哪边转 |
|---|---|---|
| 前进 + 推右 | 右 | 向右偏 |
| 后退 + 推右 | 右 | 向左偏（车尾往右，车头自然往左） |

这就是**方向盘惯例**：真车倒车时往右打方向盘，车尾往右走。
（不取反是**坦克/ROV 惯例**：不管前进后退，车体一律顺时针转。两种都自洽，
这里选方向盘惯例；想换回坦克惯例，把 `joyToMotorTargets()` 里的
`dir` 恒为 `1.0f` 即可，三处同步。）

> 代价：摇杆前后经过中点时，转向会翻一次。真车也是这样 —— 停着不动时怎么打
> 方向盘都不会转弯。摇杆 y 有死区，所以这个翻转发生在"后退 → 死区 → 前进"
> 之间，那一段本来就是原地自转，不是边走边转。

### 这两个符号是一对，必须一起定

「推右 → 车头往右转」这件事由**两个符号**共同决定，它们互为因果：

| # | 符号 | 怎么定的 |
|---|---|---|
| 1 | 摇杆：推右 → `X` 是**正**数 | **实测**。2026-10-03 用 `tools/joy_check.py` 测出这颗模块推右读到的是负数，固件用 `JOY_X_SIGN = -1` 掰正。屏幕上的点、底部 X 条、串口 `X=`、电脑上的 `--mock` 全用这一套 |
| 2 | mixer：`X=+1` → **左**路出力多 | **差速车运动学**：左快右慢，车头往右偏。电脑上的模拟器算的就是这套 |

> ⚠️ **只改其中一个、另一个不动，方向就会反过来。** 2026-10-03 前两次改不对
> 就是栽在这：改摇杆符号会连带把左右出力对调，改 mixer 又会连带把屏幕上的 X
> 对调，单动一个永远自相矛盾。所以下面三处的这两行**必须同步**：
> `src/main.cpp` 的 `joyToMotorTargets()`、`tools/motor_sim.py` 的
> `motor_pulses()`、`tools/test_firmware_logic.py` 的 `joy_to_targets()`
> （自检会检查前两者是否一致，忘了改会报错）。

**真船上还要再验一次**：两个推进器若是对称反装的（或某一路相线反了），实际
转向会和上面相反 —— 那和摇杆、和代码都没关系，是电机装法/接线的事。
接上电机后跑：

```bash
python3 tools/joy_check.py
```

它会先验链路（端口占用、波特率、行速率），再让你推摇杆、看真船，最后直接
给出结论：**`joyToMotorTargets()` 那两行要不要对调**。
（历史教训记在 `docs/ERROR-REPORT.md`：当时拿自己写的模拟器当选真值 ——
自己出题自己判卷，当然说"通过"。）

### 满油门是 2000 不是 3000 µs

需求里提到过 3000µs。这个固件是**直接输出 PWM**的，技术上想输出多少都行，
但：

- 常规电调的行程是 **1000~2000µs**，3000µs 超出行程，电调多半把它当**无效
  信号**（不动 / 报警 / 进失控保护），而不是"更大的油门"，更不会更快。
- 想真的用 3000，必须先量出你那台电调的实际行程（示波器或逻辑分析仪看
  信号线），再同时改 `src/main.cpp` 的 `PULSE_MIN` / `PULSE_MAX`。

改的时候注意：`tools/motor_sim.py` 和 `tools/test_firmware_logic.py` 里有同名
常量，测试会检查两边一致，忘了同步会直接报错。

### 几个关键概念

**开机自动校准（为什么必须校准）**

PS2 摇杆是两个电位器，机械零点和 ADC 都有误差，所以「松手时的读数」几乎不
可能是理想的 2048。不校准的话，松手时程序会以为你一直在推，**电机就自己转**。

所以**上电时提示「请松开摇杆」那 1.2 秒手不要碰摇杆**。之后想重校，**长按
SW 超过 0.8 秒**即可。

**按键的两种操作**

| 操作 | 效果 |
|---|---|
| 长按（≥0.8s） | 重新校准中点（只有中点漂了才需要） |

短按不做任何事 —— 摇杆本来就不需要按键。

**双缓冲刷屏**

`clearDisplay()` 只清 ESP32 内存里的缓冲，`display.display()` 才把 1024 字节
推给屏。代码还拿当前缓冲和上一帧 `memcmp` 比较，**画面没变就不刷**——
I2C 刷一整屏要 ~25ms，这个优化省下很多带宽。

**控制与刷屏分开节拍**

电机控制跑 `CONTROL_MS = 8ms`（约 125Hz，要跟手），刷屏跑 `DRAW_INTERVAL_MS
= 25ms`（约 40fps，I2C 屏的极限），遥测跑 50ms。三个互不拖累。

## 串口输出

每 50ms 一行，供电脑上的 Motor-Sim 监视（也可以直接看）：

```
=== 03 摇杆双电机遥控器 ===
=== 摇杆校准 ===
请松开摇杆，不要用手碰它...
X 中点 = 1908   Y 中点 = 2135   (理想值 2048)
满量程 ±1535  (= 1.24 V 摆幅)
校准完成。
CAL XC=1908 XSL=1535 XSH=1535 YC=2135 YSL=1535 YSH=1535
OLED OK: 128x64 @ 400000 Hz I2C (addr 0x3C)
开机预热 3000 ms 后摇杆自动生效；长按 SW (>0.8s) 重新校准中点。
JOY JX=2704 JY=1912 X=+0.520 Y=-0.150 MAG=0.542 OUT READY=1 L=1718 R=1282 TL=1718 TR=1282
```

- `L/R` = **实际写给 LEDC 的脉宽**（经过限速）
- `TL/TR` = 摇杆算出的目标脉宽（没限速）
- 两个不相等就说明正在加速/减速过程中

如果中点离 2048 特别远（比如 500 或 3600），说明线接错或摇杆坏了。

## 电脑端平面模拟器（Motor-Sim）

`tools/motor_sim.py` 读上面的遥测，把运动用差速运动学在电脑上跑出来，
**接电机之前先看运动对不对**。它**只读**，不向板子发任何指令。

```bash
# 看有哪些串口
python3 tools/motor_sim.py --list

# 实时仿真（先关掉 PlatformIO 的串口监视器，串口只能被一个程序占用）
python3 tools/motor_sim.py --port /dev/cu.usbserial-A5069RR4

# 没接板子也能看界面（本地造数据）
python3 tools/motor_sim.py --mock
```

| 按键 | 作用 |
|---|---|
| `W A S D` | 推/拉模拟摇杆（**仅 `--mock`**） |
| `0` | 复位原点 |
| `T` | 清空航迹 |
| `Q` / `Esc` | 退出 |

> `--mock` 照着固件的行为模拟：**前 3 秒是预热窗口**，这期间按 WASD 车不动、
> 输出固定 1500；3 秒后自动开始响应，不需要按任何键。
> 按 `D` 相当于把摇杆**推到右边**（`X` 变正），和实机一致 —— 这个符号是
> 2026-10-03 用 `tools/joy_check.py` 实测校正过的；在那之前摇杆的 X 恰好是
> 反的，于是出现过"模拟器里按右、真船往左"的怪现象。

窗口左边是俯视的平面运动（略微长方形的船体 + 航迹），右边是链路状态、
摇杆读数、左右脉宽条形图。**它用的是固件报的实际 `L/R` 脉宽**，所以屏幕上的
运动和电机拿到的完全一致。

启动时会先用 `lsof` 查这个串口有没有被别的程序占着。串口波特率由它自己设成
115200，不依赖上一个程序留下的值 —— 串口停在 9600 时读 115200 的数据，症状
是"能收到字节但一行都不完整"，很容易被当成硬件坏了。

面板里有一行 **「本程序 CPU」**：空闲时应该接近 0%。它一开始是每读不到数据
就立刻重试（忙等），实测吃掉**一整个核（99%）**、把电脑风扇拉满；现在改成
用 `select` 等数据，同一个循环实测 **0%**。这行数字就是防止它再退化的哨兵。

> Motor-Sim 零第三方依赖：串口用标准库 `termios` 直接配，不需要 pyserial。

## 实机体检（joy_check.py）

`tools/joy_check.py` 是一条命令跑完的硬件体检，**只读串口**：

```bash
python3 tools/joy_check.py            # 自动找串口
python3 tools/joy_check.py --selftest # 不接硬件，只验判决逻辑
```

1. **先验链路**：端口有没有被别的程序占着、行速率是不是 20 行/秒左右、
   固件是不是真的在发遥测。链路不过关就不往下测 —— 拿残缺数据当证据是
   2026-10-03 翻车的直接原因。
2. **再验摇杆**：松手 → 左右推到底 → 上下推到底，报告每根轴的实际跨度和
   中点，并且能区分「推左右时动的是 JY」（URX/URY 接反）这种典型情况。
3. **最后验方向**：推右保持住，读出屏幕 X 的正负；再问你两件只有眼睛能
   看到的事（推上是不是前进、推右船头往哪边转），然后直接给出**要改哪一行**。

## 手柄在电脑上：PC_CONTROL 模式

比赛现场的链路是「**Xbox 手柄 → 电脑 → 串口 → 板子**」。电脑负责把手柄读数翻译成
`nx`/`ny`，板子只管 mixer + 驱动电机，并照常回传遥测：

```
Xbox 手柄 ──USB/蓝牙──> 电脑（pad_bridge.py） ──串口 115200──> ESP32 ──> 电调
                            ↑                                    │
                            └────────── 遥测（L/R、状态）─────────┘
```

**为什么这么接最省事**：固件里 `mapAxis()` 之后的 `nx`/`ny` 是一条干净的分界线，
所以"换个输入来源"只需要换掉这两个数的来路 —— mixer、限速、OLED、模拟器、
`joy_check` 全都不用动。

### 怎么跑

```bash
pip install pygame pyserial

# ① 先认轴和按键（只读手柄，不碰串口）：推摇杆、按各个键，看哪个编号在动
python3 tools/pad_bridge.py --show-input

# ② 正常跑。启动时按一下你想当安全键的那个键（它自己学编号），
#    然后**默认是锁着的**：按一下解锁，再按一下锁上。
python3 tools/pad_bridge.py

# ③ 第一次调试不想管锁
python3 tools/pad_bridge.py --no-deadman

# ④ 不接板子，只测手柄
python3 tools/pad_bridge.py --no-serial
```

发出去的是每 20ms 一行：`CMD nx=+0.420 ny=-0.170 en=1`
（`nx`/`ny` 是 -1~+1；`en=1` = **已解锁**，`en=0` = 锁着 → 板子强制中立）。
字段顺序无关，未知字段会被忽略。

### 固件这边

`src/main.cpp` 顶上：

| 开关 | 说明 |
|---|---|
| `#define PC_CONTROL 1` | 1 = 电脑手柄模式；**0 = 回到板载 PS2 摇杆**（那套代码完整保留在 `#else` 里） |
| `#define PC_TIMEOUT_MS 200` | 多久没收到指令算断流 → 强制中立 |

### 两道安全闸（都在板子上，脚本挂了也有效）

1. **断流保护**：连续 200ms 没收到合法指令 → 回中立。脚本崩了、线掉了、
   电脑睡了，都会触发。
2. **安全键（开关式）**：**默认锁住**，按一下解锁、再按一下锁上。
   启动时脚本会让你**按一下**想当安全键的那个键（建议右肩键 RB），它自己学
   编号 —— 不去猜"RB 是几号"，因为手柄固件、有线/蓝牙、不同平台都可能不一样。
   想跳过学习直接指定：`--deadman N`；完全不想要安全键：`--no-deadman`。
   **手柄一掉线会自动重新锁上**（安全优先）。

### OLED 上怎么看出锁没锁

电脑手柄模式下，左上角第一行就是锁的状态（不用改绘图代码，`renderFrame()`
本来就在那儿画状态字）：

| 屏幕 | 含义 | 此时推摇杆 |
|---|---|---|
| `LOCK` | 锁着 | **不动**（两路 1500） |
| `UNLOCK` | 已解锁 | 正常出力 |
| `NOLINK` | 电脑那边没在发指令（断流 / 脚本没跑） | **不动** |

第二行的 `DEAD` / `OUT` 表示**此刻有没有在出力**（没连上、锁着、还在预热、
或摇杆在中点都会是 `DEAD`）。

（摇杆模式下第一行还是 `WAIT`/`READY`，表示开机预热那 3 秒。）

### 轴反了怎么办（先看这段，别急着改）

约定是"推右 = `nx` 正数、推上 = `ny` 正数"。

`pad_bridge.py` 顶上那两个系数 `PAD_X_SIGN` / `PAD_Y_SIGN` 是**实机实测**出来的
（2026-10-06，Xbox Series X 手柄 / macOS / SDL 2.28）：这只手柄的轴 0 推右为正、
轴 1 **推上为正**。

> ⚠️ **坑**：SDL 的"手柄标准映射"文档说 Y 轴是"下 = 正"，但 pygame 的
> `get_axis()` 读的是**原始 HID 轴**，不是 SDL 映射后的值 —— 两者 Y 方向相反。
> 照文档写就会反。这正是"符号没实测就写下来"的第 N 次翻车，记在
> `docs/ERROR-REPORT.md` 里。

换手柄/换平台后方向不对：要么改那两个系数，要么用 `--invert-x` / `--invert-y`
（临时覆盖）。**别去改固件里的符号** —— 那几个是给板载摇杆用的。

**为什么值得写这些**：OLED 只有 128×64，元素一多就很容易在**某个特定摇杆
位置**上撞在一起（这次开发中就被自检抓出了 4 处：底部第二条横线越界、
中点竖线顶到文字、L/R 被摇杆点压住、DEAD 文字压在圆环上）。手动试很难穷举，
脚本几秒就能扫完几千帧。

> `verify_layout.py` 的常量必须和 `src/main.cpp` 同步；`test_firmware_logic.py`
> 会顺便检查映射常量和 `motor_sim.py` 一致。改坐标/改量程后记得跑一遍。

## 出错排查

| 现象 | 检查 |
|---|---|
| 屏幕全黑，串口报 `OLED 初始化失败` | SDA/SCL 接反了？VCC 是不是 3.3V？ |
| 屏幕全黑但串口正常 | 屏的地址可能是 **0x3D**，改 `I2C_ADDR` |
| 屏幕亮但花屏 | SCL/SDA 虚接或线太长；把 `OLED_I2C_HZ` 降到 100000 |
| **上电电机就转** | 电调中立位猜错了！断电，改 `PULSE_NEUTRAL`（单向电调是 1000） |
| 推杆没反应 | 还在 3 秒预热里（左上角 `WAIT`）；或 URX/URY 接线松动 |
| 只有一个电机转 | 另一路的信号线或共地没接好 |
| 两个电机转向相反 | 电机线两两对调（无刷电机任意对调两根相线） |
| 左右转方向反了 | **先跑 `python3 tools/joy_check.py`**，别自己猜（见上） |
| 推杆时某一个轴完全不动 | 跑 `tools/joy_check.py`：它会区分"接线对调"和"那一路没读到" |
| 串口收到的行残缺、两行粘连 | 端口被别的程序占着：`lsof /dev/cu.usbserial-A5069RR4` |
| 串口全是乱码、一行都凑不齐 | 波特率不是 115200（串口会残留上一个程序留下的设置） |
| 松手后电机慢慢转 | 校准的时候手碰到了摇杆；长按 SW 重校 |
| 摇杆数值一直跳 | 正常，ADC 有噪声；把 `SMOOTHING` 调大 |
| 烧录后反复重启 | 有东西接到了 GPIO33~37（PSRAM 脚） |
| 电脑风扇狂转 | 看模拟器面板里的「本程序 CPU」：空闲时应接近 0%，贴着 100% 就是读取又在忙等 |

**左右转方向反了怎么办**：跑 `python3 tools/joy_check.py`。它对四种组合
（推右时 X 是正是负 × 推右时船头往左还是往右）各给一套明确的改法，包括
「改摇杆符号」和「改 mixer」这两处该不该一起改 —— **只改一处会把船弄反**，
这正是 2026-10-03 翻车的方式。不管怎么改，`tools/motor_sim.py` 的
`motor_pulses()` 和 `tools/test_firmware_logic.py` 里同样的两行都要同步，
否则自检会报错。

## 实验（改代码看现象，这是自学的正确姿势）

1. **改死区**：`JOY_DEADZONE` 改成 `0.05f` / `0.40f`，看内圈点线怎么变，
   什么时候左上角才从 `DEAD` 跳到 `OUT`
2. **改滤波**：`SMOOTHING` 改 `1.0f`（不滤波）看数字跳多厉害；改 `0.15f` 体会
   「平滑 vs 延迟」的取舍
3. **改限速**：`SLEW_US_PER_MS` 改成 `10.0f` 体会油门变直接；改成 `0.5f`
   看缓慢加速。想更安全就往小改
4. **加倒车提示**：`inDead` 之外再判断 `ny < -JOY_DEADZONE`，在屏幕上显示 `REV`
5. **画航迹**：把 `renderFrame()` 开头的 `clearDisplay()` 去掉，屏幕上会留下
   摇杆轨迹（注意屏幕会慢慢涂满）
6. **接 02 课的 RGB 灯**：`nx > 0.6` 亮红、`nx < -0.6` 亮蓝，把"读模拟量"和
   "写数字量"串起来
7. **加第三个设备**：I2C 是总线，把 MPU-6050 也挂到 GPIO8/9 上（地址不冲突即可），
   屏幕上同时显示姿态
