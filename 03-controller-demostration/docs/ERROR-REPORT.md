## 一、这个项目是什么

一块 ESP32-S3 独立完成：**读 PS2 摇杆 → 算差速 → 直接输出两路 50Hz PWM 驱动两个电调 → 同时把同一份数据画到 OLED**。
电脑端 `tools/motor_sim.py` 读串口遥测做平面仿真（**只读，不写串口**）。

### 硬件接线（用户确认**没有插错**，不要再让用户查线）

| 部件 | 引脚 |
|---|---|
| 摇杆 URX | GPIO1（ADC1_CH0） |
| 摇杆 URY | GPIO2（ADC1_CH1） |
| 摇杆 SW | GPIO3 |
| 摇杆 +5V | **必须接 3.3V**（不是 5V） |
| 摇杆 GND | GND |
| 左电调信号 | GPIO4 |
| 右电调信号 | GPIO5 |

- OLED：4 脚 I2C，SSD1306，地址 0x3C，128×64
- 电调：50Hz，脉宽 1000–2000µs，中立 1500（`PULSE_NEUTRAL`）
- 板子配置按 **N16R8（16MB Flash）**，串口 `/dev/cu.usbserial-A5069RR4`

## 三、待修问题（按优先级）

### 问题 1 ★最重要：左右转向方向未确定

**现象**：用户报告"左右搞反了"。我是**推测**了两次方向去改，两次都错。

**固件当前代码**（`src/main.cpp` 的 `joyToMotorTargets`）：

```cpp
targetL = unitToPulse(y - x);
targetR = unitToPulse(y + x);
```

即 `X=+1`（往右推）→ 左路 1000、右路 2000。

**仿真器 `tools/motor_sim.py` 的 `motor_pulses()` 已同步为同样映射**，
但它的**偏航角速度用的是标准差速公式**：

```python
omega = (r - l) * self.max_speed / self.wheelbase
```

**为什么改不对**：两个电机在船体上可能是镜像安装的（或相线反接），
所以"哪路出力多"和"船往哪边转"的对应关系**只能实机测出来，不能从代码推导**。
我之前的错误做法是：改了映射 → 用自己写的仿真器自测"通过" → 交给用户 →
还是反的。**拿没校准的仿真器当选真值是错的。**

**正确做法**：
1. 烧当前固件
2. 只推一次摇杆向右到底，**记录两件事**：(a) 船/电机实际往哪边转；(b) 串口那行的 `L=` 和 `R=`
3. 据此二选一：
   - 若要改方向 → **同时**改 `src/main.cpp` 的 `joyToMotorTargets()` 两行的 `-x`/`+x`，**和** `tools/motor_sim.py` 的 `motor_pulses()` 的返回值顺序（`test_firmware_logic.py` 会检查两边一致，忘改会报错）
   - 若映射本来就对、是仿真器显示反了 → 改 `tools/motor_sim.py` 里 `Robot.step()` 的 `omega` 符号（把 `(r - l)` 改成 `(l - r)`），并同步 `turn_rate_deg()`
4. **不要再靠仿真器验证方向**，必须在真机上看

### 问题 2：串口读取线程忙等烧 CPU（已部分修复，需复查）

**现象**：用户报告"电脑要爆炸了"。实测残留的 `motor_sim.py` 进程跑了 9 小时、
累计 CPU 12 分钟、瞬时占用 **137%**。

**根因**：`SerialReader._loop()` 在 `O_NONBLOCK` + `VMIN=0/VTIME=0` 下：

```python
except BlockingIOError:
    continue          # ← 端口没数据时立刻重试，满核空转
```

**已做的修复**（`tools/motor_sim.py`，语法已验证通过）：
- `_open()` 里把 `VMIN=0, VTIME=1`（让 `os.read` 最多阻塞 0.1s）
- `_loop()` 里两条 `continue` 前都加了 `time.sleep(0.005)`

**待复查**：改完**没有实测过 CPU 占用**。请用 `ps -p <pid> -o %cpu,time` 或
活动监视器确认空闲时接近 0%（而不是一个核跑满）。

### 问题 3：界面 33fps 全量重绘（未修复）

`motor_sim.py` 的 `tick()` 每 30ms 无脑 `canvas.delete("all")` + 全量重画，
摇杆静止时也在重绘，是 WindowServer 吃 CPU 的一大来源。

**建议**：加"画面指纹"（位置/朝向/脉宽/按键状态），没变就跳过重绘。
注意：`tick()` 仍要按 30ms 跑（串口解析和物理积分依赖它），只是**跳过 draw**。

### 问题 4：我写的监控脚本本身有 bug（已废弃，别再复用）

我用临时脚步读串口做诊断时，**两次解析写错**，并据此得出了错误结论：

```python
# 错误写法：' X=' 会先匹配到 'JX='，于是把原始 ADC 当成了归一化值
nx = float(s.split(" X=")[1].split()[0])
```

正确做法是**逐 token 解析** `key=value`：

```python
kv = {}
for tok in line.split():
    if "=" in tok:
        k, v = tok.split("=", 1)
        kv[k] = v
```

**教训（接手者请务必避免）**：macOS 上多个进程可以同时打开同一个 `/dev/cu.*`，
**字节会被随机瓜分**。我因此收到过残缺行、两行粘连、只有 6% 的字节量，
并把这些垃圾数据当成硬件故障的证据，连续几轮误导用户去查线。
**读串口前必须先确认端口没被别的进程占用**（`lsof /dev/cu.<port>`）。

### 用户实测的结果（2026-10-03 晚，跑 `tools/joy_check.py`）

链路这次是干净的：19.7 行/秒（固件设计值 20），第一行遥测就是
`JOY JX=1828 JY=1875 X=+0.000 Y=-0.001 MAG=0.001 DEAD READY=1 L=1500 R=1500`。

| 事项 | 实测 | 结论 |
|---|---|---|
| X 轴读不读得到 | 推左右时 **JX 跨度 4095**（0→4095） | **X 轴一直是好的** |
| 那次"X 轴不动" | 中点 `JX=1828`，而当时采到的是 1823~1831 | 就是在**摇杆停在正中**时采的样。上一节第 2 条的推测证实了：**不存在硬件故障，"直接矛盾"是测量假象** |
| 推右时 X 的符号 | 推右 → **X = -1.00（负）** | 模块的 X 电位器方向和文档约定相反，见下 |

**已据此改掉的一处（`src/main.cpp`）**：新增 `JOY_X_SIGN = -1.0f`，在
`loop()` 里 `nx = JOY_X_SIGN * mapAxis(...)`。

为什么必须改：这不只是"显示反了"——电脑端 `--mock` 里按 `D`（推右）产生的是
`X=+1`，而实机推右产生的是 `X=-1`，**两边符号相反**，于是同一个"推右"动作在
模拟器和真机上会让车朝相反方向转。用户看到的就是"在 Python 里模拟时左右被
调转"。不是摇杆坏了，也不是模拟器错了，是**固件没有遵守自己文档里写的约定**
（README 与代码注释都写"X 正数 = 右"）。

**紧接着又发现一个**：改完 `JOY_X_SIGN` 之后，用户报"前进时左右是对的，后退
时左右是反的"。查下来不是符号错 —— `r - l = (y-x) - (y+x) = -2x`，**和 y 无关**，
所以推右时车头的转动方向前进后退完全一样；不一样的是**车身往哪边漂**（前进
往右、后退往左）。这是两种驾驶惯例的区别：

| 惯例 | 推右（后退时） | 谁在用 |
|---|---|---|
| 坦克/ROV | 车体顺时针，车尾往**左** | 差速驱动的默认写法 |
| 方向盘（真车倒车） | 车尾往**右** | 用户要的，已按它实现 |

所以 `joyToMotorTargets()` 里加了 `dir = (y < 0) ? -1 : +1`，后退时把 turn 取反，
**三处（main.cpp / motor_sim.py / test_firmware_logic.py）同步**。
代价是 y 穿过中点时转向会翻一次 —— 真车也这样（停着不动怎么打方向盘都不转）。

**还剩一件事没测**：以上全是软件内部的自洽，**真船一次都没验过**。接上电机后
必须重跑 `python3 tools/joy_check.py` 第 6 步（推上是不是前进、推右船头往哪边
转），由它决定 `joyToMotorTargets()` 里 mixer 那部分要不要对调。
**在此之前不要凭感觉动那两行** —— 这正是前面连反两次的地方。

### 圆点的上下方向：**减号**，别再改成加号

`renderFrame()` 里现在是：

int dotY = cy - (int)lroundf(ny * ry);   // 推上 -> 点画在上面

因为屏幕坐标 y 是**向下**增大的，而约定是"推上 = `ny` 正数"，所以必须减。

### 对原报告两处说法的更正

1. **"问题 4"里那条解析 bug 的诊断是错的。** `s.split(" X=")`（**前面有空格**）
   不会匹配到 `JX=` —— 要匹配得写 `split("X=")`（没有空格）。照原报告那样
   改，会以为解析已经修好了，其实没修。正确做法仍然是逐 token 解析
   `key=value`（`motor_sim.parse_joy()` 就是这么写的，直接用）。

2. **"X 轴读数与 OLED 圆点在动直接矛盾"这个警报，很可能不成立。**
   那次 12 秒采到的 `JX 1823~1831 / X -0.002~+0.003` 是**自洽**的：如果当时
   `calX.center ≈ 1828`，这一组数就是"摇杆**停在正中间没动**"的正常样子，
   而不是"读到硬件故障"。也就是说：那次很可能是**在摇杆没被推的时候采的样**。
   —— 这是我基于数据的推测（未验证），`joy_check.py` 第 3 步就是用来证实或
   推翻它的：真的有 200 以上跨度，说明 X 轴一直是好的。

   还有一条更基本的推论，原报告没用上：**固件对两轴是完全对称的**（同一段
   循环、同一套 `mapAxis`、同样 11dB 衰减、相邻两个引脚），Y 能动而 X 不动
   说明不了固件有问题。所以第 3 步在 X 不动时会直接建议**把 URX/URY 两根线
   对调再测一次**——不用拆任何东西，就能分清问题在模块那一边还是 ESP32
   这一边。
